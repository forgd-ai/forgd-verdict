# CREDENTIALS.md

Every credential forgd-verdict needs, where it comes from, and where it goes.
Verified 2026-09-17 against the live Anthropic docs.

**The test suite needs no secrets, and `ci.yml` has none.** It runs offline:
the ASGI app is driven in-process and signatures are minted inside the job.
Do not add a repository secret to make CI pass. If the test suite needs
a credential, something has been wired wrong.

**No workflow in this repository reads a credential of the deployment.**
The only `secrets.` reference is `GITHUB_TOKEN`, which GitHub supplies
itself; see the last row of § Explicitly NOT needed below.

Two things to keep true in a fork:

* **Keep deployment secrets out of Terraform state.** A module that
  composes a secret into an app's secret store writes it to state in
  plaintext, which makes the state as sensitive as the credentials. The
  Kubernetes path takes them from a Secret in the cluster instead. State
  still names every resource a destroy would reach, so keep it private and
  versioned, readable only by the infrastructure identity.
* **Keep the infrastructure identity off tag-triggered workflows.** An
  identity that can create resource groups and assign roles is a much
  larger grant than one that pushes images and rolls apps. Run it from a
  `workflow_dispatch` workflow, pin its OIDC trust to an environment, and
  restrict that environment's deployment branches to `main`.

## Prerequisites that are not credentials

Both gate everything below, and both need a role that Admin does not
have.

| Thing to turn on | Where | Role required |
|---|---|---|
| Inference hooks → *Allow for your organization* | claude.ai → Organization settings → Data and privacy → Inference hooks | Owner or Primary owner (`organization:manage`) |
| Compliance API | claude.ai → Organization settings → API | Primary owner (enables at the **parent** organization; cascades to all linked orgs) |

Two traps before you touch the Compliance API toggle:

* **Turning it off stops recording, unrecoverably.** While off, no activity
  events are recorded, and on Claude Enterprise local session transcript
  capture stops too. Content from sessions that ran while it was off is never
  recoverable. Turning it back on resumes from that point only.
* **Claude Enterprise parent organizations do not appear in Claude Console.**
  If you are hunting for this in `platform.claude.com`, you are in the wrong
  place. Compliance Access Keys are created in claude.ai.

## 1. `WEBHOOK_SECRET` — Inference hooks signing secret

**Adapter 1. Required to enforce.** Without it the server returns 503 to every
hook request, so a misconfiguration surfaces at connection-test time
instead of allowing traffic.

**You do not create this. Anthropic generates it.** It appears when you first
save an endpoint URL:

> claude.ai → Organization settings → Data and privacy → Inference hooks →
> **Configure** → enter the endpoint URL → **Next**

> ⚠️ **It is revealed exactly once and cannot be retrieved afterwards, only
> rotated.** Copy it into your secrets manager before clicking Next.

Format: `whsec_<standard-base64>`. Decode with a standard base64 decoder,
not URL-safe: a URL-safe decode derives the wrong key whenever the secret
contains `+` or `/`, which is most of the time. (Handled in
`server/signature.py`; the test suite fails if a secret holding `+` or `/`
is decoded as URL-safe.)

Set it where the server runs:

```bash
export WEBHOOK_SECRET='whsec_...'          # read by $WEBHOOK_SECRET in policy.yaml
```

| Deployment | Where to put it |
|---|---|
| Docker | `-e WEBHOOK_SECRET=...`, or `--env-file` on a 0600 file |
| systemd | `EnvironmentFile=` pointing at a 0600 root-owned file |
| Kubernetes | a `Secret`, mounted as env |
| ECS / Fargate | Secrets Manager or SSM Parameter Store ARN in the task definition |

Never bake it into the image; `deploy/Dockerfile` does not.

## 2. `WEBHOOK_SECRET_PREVIOUS` — rotation overlap

**Only populated while rotating.** Rotation (**Rotate secret** under *Request
signing*) is an immediate cutover on Anthropic's side: no request is ever
signed with both secrets, so there is no dual-signing window to rely on. But
requests signed with the *old* secret keep arriving for roughly a minute,
plus anything already in flight.

So the sequence is:

1. Set `WEBHOOK_SECRET_PREVIOUS` to the current secret's value.
2. Rotate in claude.ai; copy the new secret.
3. Set `WEBHOOK_SECRET` to the new value; restart.
4. After ~5 minutes, clear `WEBHOOK_SECRET_PREVIOUS`.

> ⚠️ **Do not rotate during an outage.** Automatic circuit-breaker recovery
> only runs while Inference hooks settings are *unchanged* since the trip,
> and rotating the signing secret counts as a change. Rotate while the
> breaker is tripped and it will never self-reset; you must turn **Enforce
> verdicts** off and on by hand.

## 3. `ANTHROPIC_COMPLIANCE_ACCESS_KEY` — adapter 3 only

**Skip this entirely unless you are running the post-hoc scanner.** Adapters
1 and 2 never call the Anthropic API.

> claude.ai → Organization settings → API → **Keys** → **Create key**

Format: `sk-ant-api01-...`. Displayed once.

**Scopes to select (exactly these two):**

| Scope | Why |
|---|---|
| `read:compliance_activities` | the Activity Feed, for the `inference_hooks_request_denied` join |
| `read:compliance_user_data` | session metadata and transcripts |

> ⚠️ **Do not grant `delete:compliance_user_data`.** Adapter 3 is read-only
> and will never call a delete endpoint. Granting it means a leaked key can
> permanently destroy chats, files and projects across every linked
> organization.

Scopes are immutable after creation. To change them, create a new key
and delete the old one.

Understand what this key can read before you create it, and create one
single-organization key per `compliance.orgs` entry; see
[which organizations a key reads](PLATFORM.md#which-organizations-a-compliance-access-key-reads). Anthropic's own guidance is to treat it like production
database credentials. Keep it out of the verdict server's environment
entirely: run adapter 3 as a separate scheduled job, so a compromise
of the internet-facing server does not hand over the whole corpus.

```bash
export ANTHROPIC_COMPLIANCE_ACCESS_KEY='sk-ant-api01-...'
forgd-verdict compliance sessions --family local --join
```

Rotation has no grace period: deletion takes effect on the next request. So
create the new key, switch, verify, *then* delete the old one. Stored
pagination cursors survive rotation (they are scoped to the organization, not
the key).

If it leaks: delete it immediately, then audit
`activity_types[]=compliance_api_accessed` filtering on
`actor.api_key_id == <the compromised key>`.

## 4. `FORGD_SHARED_HEADER` — optional second factor

A static header value checked alongside the signature. Useful when the
endpoint hostname is shared or guessable. Never a substitute for signature
verification.

This one is set in two places and they must match:

1. **Anthropic side**, in Inference hooks → **Configure** → *Custom request
   headers* (up to 16).
2. **Your side**, in `policy.yaml`:
   ```yaml
   server:
     required_headers:
       x-forgd-shared: $FORGD_SHARED_HEADER
   ```
   `forgd-verdict policy` and the dashboard's Policy tab show each header
   name, with a literal value as `<redacted>`. On the Helm chart the value
   comes from the key `shared-header` (`$FORGD_SHARED_HEADER_<NAME>` from
   `shared-header-<name>`) on the verdict server alone, and a literal value
   in the policy is refused. A value that resolves to nothing stops the
   verdict server at start rather than dropping the header from the check.

Anthropic-side gotchas:

* Values are write-only: after saving, only header *names* are shown.
  Saving any change to the headers requires re-entering every value.
* **Changing the endpoint URL clears all stored header values** so your
  credentials are never sent to a new destination. Re-enter them after a URL
  change, or every request starts failing the check.
* Header names must use HTTP token characters with `-` not `_`, and must not
  collide with reserved names (`Content-*`, `Host`, proxy/cookie headers,
  `X-Forwarded-*`, `webhook-*`, or the `X-Anthropic-*` prefix).
* **Test connection** uses the values *currently in the form*, not the saved
  ones. Re-enter them before testing.

## 5. `FORGD_METRICS_TOKEN` — gates `/metrics`

No Anthropic involvement. `GET /metrics` on the verdict server, and
`GET /stats` on the collector and the intake, require
`Authorization: Bearer $FORGD_METRICS_TOKEN`.

**Empty means the endpoint is disabled and returns 404.**
`deploy/Caddyfile` blocks `/metrics` at the proxy, but a platform with
all-or-nothing ingress (Container Apps, Cloud Run, App Runner) has no
equivalent, so an unset token there would publish the endpoint. It carries no
matched content (the privacy invariant holds), but it does expose your
request volume, which Claude surfaces are in use, and your deny rate.

A placeholder such as `changeme` counts as empty. A token under 24
characters stops the verdict server and the collector from starting.

```bash
export FORGD_METRICS_TOKEN="$(python3 -c 'import secrets;print(secrets.token_urlsafe(32))')"
curl -H "Authorization: Bearer $FORGD_METRICS_TOKEN" https://<host>/metrics
```

`/healthz` is unauthenticated so platform probes work. It returns
`status`, `mode`, `build`, `gitleaksd` and `uptime_s`. `build` is the
release and commit answering, and `gitleaksd` is `not_configured`, `ok`
or `down`.

## 6. `FORGD_HASH_SALT` — required, ours alone

No Anthropic involvement. Salts `Finding.excerpt_hash`.

A bare sha256 of a low-entropy value is brute-forceable (an SSN is ~10⁹
possibilities, a PAN fewer once Luhn is applied), so whoever holds your
findings could recover the value. The verdict server, the collector, the
intake and the ingest jobs refuse to start with an empty salt, with or
without a findings store, unless the policy file sets
`privacy.allow_unsalted: true`.
Generate one with `openssl rand -hex 32`.

```yaml
privacy:
  hash_salt: $FORGD_HASH_SALT
```

Setting it makes hashes incomparable across deployments and changes every
hash. Treat it as long-lived: rotating it
invalidates historical correlation.

## 6b. The OIDC subject is not what the documentation shows

Not a credential, but a mismatch here fails a CI deploy with an error that
explains nothing.

A GitHub organization with immutable OIDC identifiers enabled presents
numeric org and repo ids in the token subject:

```
repo:<org>@<org-id>/<repo>@<repo-id>:environment:<environment>
```

rather than the documented `repo:<org>/<repo>:environment:<environment>`.
A federated credential registered for the documented form fails with:

```
AADSTS700213: No matching federated identity record found for presented
assertion subject 'repo:<org>@<org-id>/<repo>@<repo-id>:...'
```

The property itself is good, since a rename cannot silently transfer trust,
but most published examples use the short form. Register a federated
credential for both forms, so the trust holds whether or not the setting
is on. The ids come from the GitHub API:

```bash
gh api repos/<org>/<repo> --jq '"org id \(.owner.id), repo id \(.id)"'
```

The AWS module trusts both forms when `github_owner_id` and
`github_repo_id` are set. Both forms carry
the repository's name, so a rename breaks both: register the pair for the
new name before renaming, and delete the old pair once a deploy under the
new name has passed. If a deploy fails this way, read the presented subject
out of the error and register it verbatim.

## 6c. Container Apps Jobs need a different role

`Container Apps Contributor` grants `Microsoft.App/containerApps/*` and
nothing on `Microsoft.App/jobs`. Assigning it to a job silently grants
no access, and the failure appears as:

```
ERROR: The containerapps job '<job>' does not exist
```

The job exists. Azure reports an unauthorized GET as absence, so the error
sends you hunting a missing resource rather than a missing grant. Jobs need
`Container Apps Jobs Contributor`.

| Resource | Role |
|---|---|
| Container app | `Container Apps Contributor` |
| Container Apps **job** | `Container Apps Jobs Contributor` |
| ACR (push) | `AcrPush` |
| Blob store (write) | `Storage Blob Data Contributor`, or while store-azure's `control_enabled` is true its custom writer role: blob `read`, `write`, `add/action` |
| Blob store (dashboard) | `Storage Blob Data Reader`, or while store-azure's `control_enabled` is true its custom reader role: blob `read` |

`deploy_azure.sh` does an explicit `job show` first so the message names
the actual cause, instead of a retry loop repeating a permission error that
will never resolve.

## 7. `AZURE_CLIENT_ID` — required, and its absence hangs rather than fails

Not a secret, but it belongs here because omitting it produces a
confusing failure.

The blob findings store authenticates with the app's user-assigned
managed identity. `DefaultAzureCredential` cannot guess which user-assigned
identity to use, and with an unnamed one it walks its entire credential
chain with retries, which does not raise: it hangs. The symptom is a
writer thread stalled forever: records queued, nothing written, `errors: 0`,
and no log line anywhere; `/metrics` shows `"written": 0` under `store`
with `pending` above 0, the stuck record counted in `inflight`. On the
intake, a batch shipped to `/intake` does not go through that writer: it
shows as `intake_writes.inflight` at its limit in `/stats`, with
`store_timeout` and `write_busy` rising and the ERROR
`intake store write timed out` in the log.

Set it to the identity's `clientId` on every app that reads or writes the
store:

```bash
az containerapp update -g "$RG" -n "$APP" \
  --set-env-vars "AZURE_CLIENT_ID=$(az identity show -g "$RG" \
    -n "$IDENTITY" --query clientId -o tsv)"
```

The code prefers `ManagedIdentityCredential(client_id=...)` when this is
present and bounds every blob call, so a misconfigured identity surfaces as
a counted error instead of a silent stall. `/metrics` also reports
`last_flush_ms`, which is what makes a slow or stuck backend visible.

## 8. Entra app registration — dashboard sign-in only

Three values, not one, and none of them reaches the dashboard. Created by
you, stored only in a Kubernetes Secret, never in GitHub.

**The dashboard signs nobody in.** It runs `dashboard.auth.mode: oidc_jwt`,
which verifies a bearer token against the tenant's JWKS (signature, `exp`,
`iss`, `aud`) and rejects anything else. oauth2-proxy sits in front, does
the interactive flow, and passes the ID token through in `authorization`.
The credential therefore belongs to the proxy. The dashboard needs the
issuer, the JWKS URL and the audience, and those are not secrets.

That split is why this is the only Entra credential in the deployment and
why it is not on the verdict server or the collector; see the warning at
the end of this section.

```bash
HOST=verdict.example.com

APPID=$(az ad app create --display-name "forgd-verdict dashboard" \
  --sign-in-audience AzureADMyOrg \
  --web-redirect-uris "https://$HOST/oauth2/callback" \
  --query appId -o tsv)

SECRET=$(az ad app credential reset --id "$APPID" \
  --display-name oauth2-proxy --years 1 --query password -o tsv)

kubectl create secret generic oauth2-proxy -n forgd \
  --from-literal=client-id="$APPID" \
  --from-literal=client-secret="$SECRET" \
  --from-literal=cookie-secret="$(openssl rand -base64 32 | tr -- '+/' '-_')"
```

The `tr` is needed: the value is written into a cookie, so it has
to use the URL-safe base64 alphabet. oauth2-proxy also requires the decoded
secret to be exactly 16, 24 or 32 bytes: `openssl rand -base64 32` gives
32, and a hand-picked passphrase almost certainly does not.

**The client id does double duty, and rotating the app registration is
therefore not only a proxy change.** It is also the audience the dashboard
verifies:

```
dashboard.auth.audience = <application client id>
dashboard.auth.issuer   = https://login.microsoftonline.com/<tenant>/v2.0
dashboard.auth.jwksUrl  = https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys
dashboard.auth.header   = authorization
```

`header` must be set. In `oidc_jwt` mode it names the header the bearer
token arrives in, and it defaults to `x-ms-client-principal-name`, the
Container Apps EasyAuth name, which carries no token.

A tenant id and an application id are not credentials, but they name your
directory, so they are supplied rather than committed, the same
treatment org ids get. They are chart values and environment variables, not
entries in `policy.yaml`.

**The redirect URI is per hostname and per proxy.** oauth2-proxy uses
`/oauth2/callback`. Container Apps EasyAuth uses
`/.auth/login/aad/callback`, so a registration carried from one to the other
keeps a URI naming a host it no longer serves.

Remove the stale URI rather than leaving it. Destroying a container app
does not destroy the Container Apps environment, so the old hostname can
still resolve, and the registration would still redirect an authorization
code to a name that anyone able to create an app in that environment could
take.

Audit the list after any change of host or proxy:

```bash
az ad app show --id "$APPID" --query web.redirectUris -o tsv
az ad app update --id "$APPID" --web-redirect-uris "https://$HOST/oauth2/callback"
```

`--web-redirect-uris` SETS the list rather than adding to it, which is what
makes that second line a cleanup. Pass every URI you intend to keep.

`--enable-id-token-issuance` is not in the create above: it turns on the
implicit grant, which EasyAuth needs and the authorization code flow
oauth2-proxy uses does not. A registration carried over from Container Apps
has it on, so turn it off:

```bash
az ad app update --id "$APPID" --enable-id-token-issuance false
```

You can check which flow is in use without signing in. Follow
`/oauth2/start` and read the `response_type` oauth2-proxy asks for; `code`
means the implicit grant is unused. Entra also validates `redirect_uri` at
the authorize endpoint before it authenticates anyone, so a registration
that no longer lists the URI answers with an `AADSTS` error page instead of
a sign-in form, which makes both of these changes checkable with `curl`.

The deployment wiring is in `../deploy/helm/README.md` § Putting oauth2-proxy
in front: which oauth2-proxy arguments are load-bearing, and the 502 and the
un-redirected `authentication_required` that come from getting them wrong.

### Rotation

```bash
SECRET=$(az ad app credential reset --id "$APPID" \
  --display-name oauth2-proxy --years 1 --query password -o tsv)
kubectl create secret generic oauth2-proxy -n forgd \
  --from-literal=client-id="$APPID" \
  --from-literal=client-secret="$SECRET" \
  --from-literal=cookie-secret="$(kubectl get secret oauth2-proxy -n forgd \
    -o jsonpath='{.data.cookie-secret}' | base64 -d)" \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl rollout restart deploy/oauth2-proxy -n forgd
```

Keeping the cookie secret across a rotation keeps existing sessions valid.
Changing it signs everyone out, which is the right move if the concern is
the cookie secret rather than the client secret. `az ad app credential
reset` REVOKES the existing password, so the proxy is broken between that
command and the rollout.

### Who can read the dashboard

`--sign-in-audience AzureADMyOrg` restricts sign-in to your tenant, so by
default anyone in the tenant can read the dashboard. Whether that is
acceptable is the deployer's choice: the store holds findings rather than
prompt content, and with `privacy.sealing` matched values only sealed to a
key the dashboard cannot decrypt with, which can make tenant-wide read reasonable for an
evaluation, but a deployment carrying a real organization's traffic should
narrow it. Two levers, and they answer different questions:

* *Assignment required* on the enterprise application, with a group
  assigned, decides who may sign in at all. Group-based assignment
  needs Entra ID P1; per-user works on any tier.
* `dashboard.entitlements.map` in `policy.yaml` decides which orgs,
  Managed Agents workspaces and intake clients a viewer who has signed in
  may read. It requires `oidc_jwt`, because a
  group membership that cannot be verified is one the caller can choose;
  the loader refuses the setting under `none` or `trusted_header` rather
  than serving a control that looks enforced.

> **Never put this in front of the verdict server or the collector.**
> Anthropic authenticates with a webhook signature and an OTLP header. An
> auth redirect makes every governed prompt a webhook failure, and
> sustained failures trip the circuit breaker.
>
> On Kubernetes the chart enforces this. It splits the
> ingress into three objects and sets
> `nginx.ingress.kubernetes.io/enable-global-auth: "false"` on the public
> one unconditionally, because that annotation defaults to true and a
> global auth snippet would otherwise front `/hook` and `/v1` however the
> objects are arranged. Only the dashboard object carries `auth-url` and
> `auth-signin`.

## 9. TLS certificate and key

Anthropic requires an `https://` URL on port 443, on a publicly routable
host, with a certificate that validates against the public CA trust store,
responding without redirects.

* `deploy/Caddyfile` obtains and renews a Let's Encrypt certificate
  automatically, with nothing to set.
* Providing your own: `tls /etc/ssl/verdict.crt /etc/ssl/verdict.key`. An
  internal CA will fail; the chain must reach a public root.
* **Reverse tunnels (ngrok and similar) are blocked by Anthropic's network
  policy.** Do not try to test through one.

## 10. `otel.orgs[].token` — adapter 4, one per org

The collector accepts an OTLP export only with a token it lists, as
`Authorization: Bearer` or `x-forgd-token`, and files the batch under that
entry's org. Generate one per org, at least 24 characters:
`openssl rand -base64 24`. Two entries may not share a token, and an entry
with a token and no `id` refuses to start.

```yaml
otel:
  orgs:
    - id: $FORGD_ORG_ID_PRIMARY
      label: primary
      token: $FORGD_OTEL_TOKEN_PRIMARY
```

On the chart it is `secrets.otelTokens.<name>`; on Container Apps the
`otel_tokens` variable of `app-aca`; on ECS and Cloud Run a secret ARN or id
per org. The same value goes in that org's exporter configuration.

**Rotation overlaps.** Add a second entry with the same `id` and the new
token, roll, switch the exporter, then remove the old entry and roll
([OPERATIONS.md](OPERATIONS.md#rotate-secrets)).

## 11. `intake.fleet[].tokens`, `intake.clients[].token`, `hook.ship_token`, `hook.scan_token` — adapter 2

The intake authenticates a laptop by its fleet's token and an agent by its
client's token: `/intake` for spooled decisions shipped at session end,
`/scan` for the remote scan. A token outside its credential's `routes` gets
403. Generate each, at least 24 characters; two credentials may not share a
name or a token.

```yaml
intake:
  fleet:
    - name: laptops
      tokens: [$FORGD_INTAKE_FLEET_TOKEN, $FORGD_INTAKE_FLEET_TOKEN_PREVIOUS]
      org: $FORGD_ORG_ID_PRIMARY
  clients:
    - name: invoice-bot
      token: $FORGD_INTAKE_TOKEN_INVOICE_BOT
      routes: [scan]
      agent: true
```

On the chart the fleet token is `secrets.intakeFleetToken` (secret key
`intake-fleet-token`, with `intake.fleet.enabled`) and the client tokens
`secrets.intakeTokens`. On ECS the fleet token is
`intake_fleet_token_secret_arn` (and `intake_fleet_token_previous_secret_arn`
while rotating), on Cloud Run `intake_fleet_token_secret_id` (and
`intake_fleet_token_previous_secret_id`), and each client a secret ARN or id
in `intake_token_secret_arns` or `intake_token_secret_ids`. On Container
Apps, which holds the values, they are `intake_fleet_token`,
`intake_fleet_token_previous` and `intake_tokens`, with `enable_intake`.

On the laptop, `hook.ship_token` (sent to `ship_endpoint`) and
`hook.scan_token` (sent to `scan_endpoint`) are the fleet's token. One
token serves both when the fleet has both routes, which is the default.
Without `hook.project_overrides: true` the hook ignores
`FORGD_VERDICT_SHIP_TOKEN`, `FORGD_VERDICT_SCAN_TOKEN` and `$VAR`
placeholders, so MDM writes the literal into the laptop's `policy.yaml`,
readable by that user and writable only by an administrator.

**The fleet token rotates with an overlap.** Set the new value as
`FORGD_INTAKE_FLEET_TOKEN` and the old one as
`FORGD_INTAKE_FLEET_TOKEN_PREVIOUS`, push the new one to every laptop
through MDM, then remove the previous one
([deploy/MDM.md](../deploy/MDM.md#rotating-it)). One device is cut off
without a rotation by denying its id
([OVERRIDES.md](OVERRIDES.md#the-allowlist)).

**A client token rotates with no overlap.** A client holds one token, and a
second client with the same name is refused, so set the new token on the
intake and push it to the agent together. Until the agent has it, its
remote scan is refused.

## 12. `dashboard.admins.form_key` — dashboard admin forms

An HMAC key for the dashboard's admin form tokens, which expire after five
minutes. The dashboard refuses to start with admin groups set and a key
shorter than 32 bytes. Generate it with `openssl rand -base64 32` and set
`FORGD_DASHBOARD_FORM_KEY`; every dashboard replica needs the same value.
On the chart it is the `dashboard-form-key` key of the Secret; on
Container Apps the `dashboard-form-key` secret; on ECS and Cloud Run
`dashboard_form_key_secret_arn` / `_id`.

**Rotation has no overlap**, and needs none: set the new value and roll.
A form open at the time is rejected and has to be reloaded.

## 13. `overrides.signing_key` — runtime overrides

The Ed25519 private key the dashboard signs runtime-override records with.
Only the dashboard and the CLI may hold it; every other service refuses to
start with it set, and verifies records with the public keys in
`overrides.verify_keys` (`FORGD_OVERRIDES_VERIFY_KEY`, comma-separated).
It must be a `$NAME` reference, `$FORGD_OVERRIDES_SIGNING_KEY` by default;
a literal key in the policy is refused. Generate a pair with
`forgd-verdict overrides keygen --private-key-file signing.key`.

**Rotation overlaps.** `verify_keys` is a list: add the new public key
everywhere, switch the dashboard's signing key, then remove the old public
key once the head is re-signed. Removing it early makes readers refuse the
records. The steps are in [OVERRIDES.md](OVERRIDES.md).

## 14. `sinks[].token` — adapter 5

The credential the collector presents to a sink's destination, created by
whoever runs that destination. A sink with an endpoint and an empty token
refuses to start; one with no endpoint is skipped. Reference it as
`$FORGD_SINK_TOKEN_<NAME>` and set it on the collector from the secret
store. On the Helm chart that is the key `sink-token-<name>`
(`secrets.sinkTokens.<name>` for a chart-managed Secret), which reaches the
collector alone; the chart refuses a literal token in the policy and
`FORGD_SINK_TOKEN_*` in `extraEnv`. The Terraform app modules do not wire
sink tokens.

**Rotation has no overlap**: issue the new token at the destination, set it,
roll the collector, then revoke the old one.

## 15. `managed_agents.workspaces[].api_key` — adapter 6

A workspace API key from the Anthropic console, which the ingest job sends
to the Managed Agents API. No read-only scope is documented for it: it can
create and delete sessions as well as read them. Reference it as
`$FORGD_MANAGED_AGENTS_KEY_<NAME>`; on the chart it is
`secrets.managedAgentsKeys`. A workspace whose key is empty is skipped with
an error.

**Rotation has no overlap**, the same as the Compliance Access Key: create
the new key, switch the ingest job, confirm a pass succeeds, then delete the
old key.

## 16. `behaviour.judge.api_key` — the session judge

An Anthropic API key the ingest job uses to ask `behaviour.judge.model`
about each session it scans ([SERVER.md § Session flags](SERVER.md#session-flags)).
Each request carries the session's transcript and is billed to the key's
workspace; [PRIVACY.md](PRIVACY.md#what-is-stored-and-where) says what is
sent. Reference it as `$FORGD_JUDGE_API_KEY`; on the chart it is
`secrets.judgeApiKey`, with `ingest.judge.enabled: true`. Give it a workspace of its own, so its spend and its
request logs are separate. Rotation has no overlap: create the new key,
switch the ingest job, confirm a pass succeeds, then delete the old key.

## When a reference resolves to nothing

A credential written as `$NAME` whose variable is unset or empty either
stops the service that reads it, or has a fixed effect that the service
logs at start as a warning naming the path and the variable, never a value.

| Path | Unset |
|---|---|
| `privacy.hash_salt` | refuses to start (unless `privacy.allow_unsalted: true`) |
| `server.required_headers.<header>` | the verdict server refuses to start |
| `dashboard.admins.form_key`, `overrides.signing_key` | the dashboard refuses to start while admins are configured |
| `sinks[].token` | refuses to start when the sink's endpoint is set |
| `server.metrics_token` | logged; `/metrics` and `/stats` are not served |
| `otel.orgs[].token` | logged by the collector; that entry's exports are refused with 401 |
| `intake.clients[].token` | logged by the intake; that client is refused with 401 |
| `intake.fleet[].tokens` | logged when every token in the entry is unset; that fleet is refused with 401. An unset previous token beside a set current one is a normal state |
| `compliance.api_key`, `compliance.orgs[].api_key` | logged by the ingest job; that org is not scanned |
| `managed_agents.workspaces[].api_key` | logged and reported in the run's summary as `no api key` |
| `behaviour.judge.api_key` | the ingest job refuses to start while `behaviour.judge.enabled` |
| `hook.ship_token`, `hook.scan_token` | the hook says so on stderr; the intake refuses the unauthenticated request, and spooled records stay spooled |

## Explicitly NOT needed

| Credential | Why not |
|---|---|
| `ANTHROPIC_API_KEY` | Nothing reads this variable. The standard API keys the project uses are adapter 6's per-workspace key, referenced as `$FORGD_MANAGED_AGENTS_KEY_<NAME>` (§15), and the session judge's, `$FORGD_JUDGE_API_KEY` (§16), each only when its feature is on. |
| Admin API key (`sk-ant-admin01-...`) | Reaches the Activity Feed **only**. Enough for `forgd-verdict compliance denials`, but the session endpoints return **403** for it — so it cannot do adapter 3's actual job. |
| Analytics API key | Different API, aggregate usage and cost. Unrelated. |
| `GITLEAKS_LICENSE` | Only `gitleaks/gitleaks-action` requires one for org-owned repos (free, but registration-gated, and the Action is `NOASSERTION`, not a standard OSS licence). CI installs the **MIT-licensed gitleaks release binary** directly, pinned by version and SHA-256, and the Docker image builds the same MIT-licensed CLI from the v8.30.1 module source, pinned by checksum in `deploy/gitleaks-cli/go.sum`, so there is no key and no non-OSS dependency. |
| Any GitHub secret for CI | The suite is fully offline. `GITHUB_TOKEN` is auto-provided by GitHub. |

## Provisioning order

```
1. Primary owner enables the Compliance API          (claude.ai → Org settings → API)
2. Owner enables "Allow for your organization"       (claude.ai → Data and privacy)
3. Deploy adapter 1 with TLS, reachable, mode: observe
4. Save the endpoint URL  -> Anthropic reveals WEBHOOK_SECRET  <- COPY IT NOW
5. Set WEBHOOK_SECRET in the server env; restart
6. (optional) Add the custom request header, both sides
7. Test connection  -> expect an allow verdict reported back
8. Shadow mode + Enforce verdicts on
9. (later, separately) Create the Compliance Access Key for adapter 3
```

In step 4 the secret is shown once, and the server
refuses traffic with 503 until it has one.

## Handling rules

* Nothing here goes in git. `policy.yaml` carries `$VAR` references only.
* `forgd-verdict policy` prints the effective config with secrets redacted.
  Use it to confirm what a deployed instance resolved, without
  printing values.
* The verdict server should not hold the Compliance Access Key. Different
  blast radius, different host.
* `archive_dir` holds full transcripts. It is not a credential, but it is the
  most sensitive thing this project writes. 0600 files, encrypted volume, its
  own retention clock, and never in git (`.gitignore` covers it).
